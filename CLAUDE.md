# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

`uparserstudio` is currently a research/reference workspace, not a standalone application. The top level of this repo has no source code of its own — it exists to hold a curated set of open-source document-parsing / OCR projects side by side under `opensource/` for study, comparison, and (eventually) extraction of ideas or code into a unified parser.

Each subdirectory of `opensource/` is a **full clone of an independent upstream repository**, complete with its own `.git`, license, dependency lockfiles, and build tooling. They are not git submodules and are not otherwise wired into this repo — `git status` at the top level just shows `opensource/` as a single untracked directory. Do not assume changes inside them are tracked by the top-level repo's history unless you check `git -C opensource/<project> status` directly.

| `opensource/chandra` | `datalab-to/chandra` | Python (`uv`, `pytest`) | Datalab's document-intelligence model/toolkit. |

| `opensource/MinerU` | `opendatalab/MinerU` | Python (`mineru/`) | PDF-to-structured-data extraction pipeline (layout analysis, formula/table recognition). |

Because each project is self-contained, **work inside one of these directories using that project's own conventions and tooling** — do not assume a shared build system, dependency manager, or test runner across them. Check for that project's own `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, or lockfile (`uv.lock`, `Cargo.lock`, `pyproject.toml`, etc.) to determine how to build/lint/test it. Notably `opensource/liteparse` ships an `AGENTS.md` with a full architecture writeup (Rust core → language bindings, spatial grid projection pipeline, OCR engine trait) that should be treated as authoritative when working in that project.

## Unified CLI product design

`ARCHITECTURE.md` documents the target design for `uparserstudio` as a unified CLI product (`uparser`) intended primarily for coding agents (Claude Code, Codex, OpenCode) to invoke as a subprocess. As of v0.6, **the core is implemented in Rust** (`uparser-core` crate, modeled directly on `opensource/liteparse`'s "Rust core + napi-rs/PyO3/wasm-bindgen bindings" pattern — Python/TS are binding-layer only, not implementation languages). As of v0.7, `uparser_core` supports six pluggable parsing protocols via a **Protocol Adapter** trait: four single-model VLM protocols (MinerU's `backend/vlm/`, dots.ocr, **MonkeyOCRv2** — target v2 in `opensource/MonkeyOCRv2`, not the v1 SRR-triplet code in `opensource/MonkeyOCR` — PaddleOCR), plus two new additions: **`native`** (zero-model, embeds the `liteparse` crate directly as a library dependency for born-digital PDFs with a native text layer — no external service at all) and **`pipeline`** (traditional multi-model layout→OCR→formula→table flow aligned with MinerU's `pipeline` backend). The `pipeline` protocol solves a specific problem the user raised: several of its models are heavy enough to saturate a client-side agent machine's CPU, so each of its four stages (layout/ocr/formula/table) independently declares a `StageBackend` — `Local` (in-process lightweight ONNX inference via the `ort` crate, only for genuinely small models like MinerU's already-ONNX table classifier/structure recognizer) or `Remote` (offload to a new second class of externalized service, a custom lightweight REST contract — not OpenAI chat-completions — dubbed "Pipeline Model Serving"). Defaults lean `Local` only for the lightweight `table` stage; `layout`/`ocr`/`formula` default to `Remote` since their original weights are torch models with uncertain ONNX portability (open question, see `ARCHITECTURE.md` §8/§11.2). Model inference is otherwise always externalized — never run in-process — via whatever service each protocol natively requires (VLM protocols through vLLM/LMDeploy OpenAI-compatible endpoints; PaddleOCR and Pipeline Model Serving through their own lightweight, non-chat-completions REST contracts), with one known exception under discussion: MonkeyOCRv2's document-dewarping preprocessor is a local-only auxiliary model with no externalized service equivalent yet (see `ARCHITECTURE.md` §8-§9 — this is part of why the "no in-process inference by default" line is held firmly, since Rust's ML ecosystem is weaker than Python's). Recommended engineering practice: prototype new protocol adapters in Python first (faster iteration while reverse-engineering a model's raw prompt/output contract from its vendored source), then port stabilized adapters to Rust (`ARCHITECTURE.md` §9.4).

As of v0.8, the design also covers: (1) **multi-format ingestion** — `ingest.rs` gains a `normalize_format()` step converting PPT/Word/Excel/images to PDF via external tools (LibreOffice/ImageMagick), reusing the approach `opensource/liteparse` already validated, shared by all six protocols; XLSX/CSV get a structured-data bypass (read cells directly, skip visual recognition entirely) — see `ARCHITECTURE.md` §12; (2) **content pre-analysis and routing** — a Profiler+Router stage runs before protocol selection, classifying documents in cost-increasing tiers (L1 format/metadata → L2 cheap structural heuristics → L3 *opt-in* low-cost model-based semantic classification) and producing a `DocumentProfile` written into `ParseResult`; `uparser classify` exposes it standalone and `--protocol auto` wires classify+route+parse — see §13.

v0.9 is an architecture-review revision that fixed several internal contradictions accumulated across v0.3–v0.8; when working on the design treat v0.9 notes as authoritative over older text: (a) the `ProtocolAdapter` trait was rebuilt around a single `async fn parse_page(page, ctx)` (with `#[async_trait]` for `dyn` safety) because the old `build_requests→dispatch→parse` linear trio **could not express two-stage protocols** (MinerU-vlm / MonkeyOCRv2, where stage-2 requests depend on stage-1's parsed layout) — adapters now drive their own multi-round orchestration internally via `ParseCtx` (§2.0); (b) a `scheduler.rs` was added for document-level scheduling, a shared cross-page concurrency budget, processing windows and streaming output for large docs (§2.2 — previously absent though both reference impls treat it as essential); (c) the IR gained `spans`/`merge_hint`/`font_size`, a `Geometry` enum (rect vs polygon) split out from `CoordinateSystem`, and a `geom_frame` for nested crop coordinate frames — because the flat v0.8 `Block` silently dropped signals MinerU's paragraph-merge/title-leveling depend on; shared `postprocess.rs` is now explicitly two-layer (pure-geometry vs signal-enhanced, degrading by each adapter's declared `emitted_signals`) and title-leveling is downgraded to an optional capability-gated LLM step, not a solved shared feature (§4.1/§5/§14); (d) the Agent-first CLI contract (semantic exit codes, stdout=result/stderr=logs, structured error object) was restored as first-class (§6.1) after eroding in v0.4–v0.8; (e) a content-hash cache layer was restored (§15); (f) the single canonical control-flow order `detect_format → structured_bypass → normalize_format → rasterize → profiler → router → parse` was fixed (§13.1a), removing the xlsx-path ambiguity, and L3 profiling was made opt-in. Routing is document-level only; page/region-level mixed-protocol routing is a deferred open question. `ARCHITECTURE.md` §8 is a historical open-issues ledger; §14/§15 and in-section v0.9 notes are the latest corrections and win on conflict. Read `ARCHITECTURE.md` before implementing any top-level CLI code.

## Working in this repo

- When asked to compare approaches across parsers (e.g. "how does layout reconstruction work in MinerU vs. liteparse"), expect to read across multiple vendored repos; each has a very different architecture and language.
- `DEVELOPMENT_PLAN.md` breaks the `ARCHITECTURE.md` design into phased, gated tasks (P0–P10, task IDs `T-<phase>.<n>`). Check it before starting implementation work to see what phase/task you're in and what its Gate requires.

Build/test/lint (run from `uparser/`): `cargo build --workspace`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`. All green by default with no extra flags/network access.

The `pdfium` feature (real PDF rasterization, via `liteparse-pdfium`) is **not** default-on: `liteparse-pdfium-sys`'s build script downloads a prebuilt PDFium binary from GitHub on first build, which isn't reliable in every environment. Opt in with `--features pdfium` when network access to GitHub releases (or a pre-populated `~/.cache/pdfium-rs`) is available; without it, `ingest::rasterize()` returns `IngestError::PdfiumFeatureDisabled`. **Confirmed working**: the download completes in ~2 minutes given enough time (past attempts that gave up at 90s were simply too impatient, not evidence the download is broken) — `cargo build --features pdfium`/`native` succeed and `ingest::tests::rasterizes_fixture_pdf` passes for real once `~/.cache/pdfium-rs` is populated. The `native` feature (§ below) pulls `pdfium` in transitively and is likewise opt-in, not default-on.

`T-0.1`–`T-0.9` (Gate G0) and `T-1.2`–`T-1.10` are implemented, and **Gate G1 is fully validated**: `adapters/mineru_vlm.rs` was run end-to-end (via `examples/mineru_vlm_smoke.rs`) against a real vLLM deployment of `MinerU2.5-2604-1.2B`, correctly extracting text/title/footer/table/image blocks (including OTSL→HTML table conversion) from real pages of a scanned 10-K filing. The mineru-vlm protocol details (custom-token grammar, image preprocessing, category vocab, OTSL/formula handling) were originally reverse-engineered from `mineru_vl_utils` **v0.1.14** (the only copy available locally; `opensource/MinerU/pyproject.toml` pins a newer `>=1.0.5` series not present on this machine) and confirmed largely accurate against the real endpoint, with one correction: **`skip_special_tokens: false` must be set explicitly in the request body** — vLLM's OpenAI-compatible endpoint defaults to stripping special tokens, which silently ate the `<|box_start|>`/`<|ref_start|>` wrapper tokens the `custom_token` grammar depends on (fixed in `layout_sampling()`/`stage2_prompt_and_sampling()`). `emitted_signals`/`provides_reading_order` (both `false` — no spans/merge_hint/reading-order signal observed from this backend) still hasn't been re-examined against real output and remains a possible deviation from `DEVELOPMENT_PLAN.md`'s assumption. `adapters/mineru_vlm.rs` is still not wired into `Registry::with_builtins()` or the CLI (no `--endpoint` flag exists yet) — that wiring, plus T-1.1's Python-prototype fixture capture, are the next steps before this protocol is user-facing.

`T-2.2`–`T-2.4` are implemented, and **Gate G2's offline-verifiable half is done**: `adapters/dots_ocr.rs` (single HTTP round-trip, strict-JSON output, no `spans`/`merge_hint` signal — structurally the opposite of mineru-vlm's two-stage flow) reuses `geometry.rs`/`category_map.rs`/`postprocess.rs`/`render/` via purely additive functions — `postprocess.rs` and `render/` got **zero** code changes, only new tests proving they already handle dots.ocr-shaped `Block`s identically to mineru-vlm-shaped ones. Unlike mineru-vlm, dots.ocr's protocol source is **fully vendored** in `opensource/dots.ocr` (no external-package version-mismatch risk), read directly from `image_utils.py`/`prompts.py`/`layout_utils.py`/`output_cleaner.py`/`inference.py`. One confirmed deviation from `DEVELOPMENT_PLAN.md`'s assumption: dots.ocr's bbox coordinates are **plain absolute pixels of the model's resized input image**, not a `Norm0To1000` normalized space — `coordinate_system()` returns `PixelAbs` and `parse_page` does the resized→original pixel conversion internally via the new `geometry::rescale_bbox_to_original`. No dots.ocr vLLM endpoint has been available to validate end-to-end (unlike mineru-vlm) — `examples/dots_ocr_smoke.rs` exists and is ready to run the moment one does; until then, treat this adapter's fidelity as offline-verified only.

`T-3.2`–`T-3.4` are implemented, and **Gate G3 is done**: `adapters/monkeyocr_v2.rs` (`opensource/MonkeyOCRv2`, fully vendored — not the v1 SRR-triplet code in `opensource/MonkeyOCR`) is a third, structurally distinct protocol (its own resize strategy, its own Python-literal-list raw output format requiring a hand-written recursive-descent parser since the real service parses via `eval()` and JSON won't cover single-quoted strings) that reuses `otsl.rs` and `formula_repair.rs` **completely unmodified** — verified both by the fact that this session never edited those two files and by an explicit adapter-level test asserting the shared `formula_repair::DEFAULT_CHAIN` correctly repairs a malformed formula inside the MonkeyOCRv2 pipeline. `category_map.rs` gained a third mapping function (`map_monkeyocrv2_category`, 10 Title-Case categories, near-identical spelling to dots.ocr's vocab) and `geometry.rs`/`imaging.rs`/`output_parse.rs` each gained one more additive, protocol-specific function — the shared/reused-vs-new split is exactly what Gate G3 was designed to measure. Document dewarming preprocessing (an independent local-torch model in the real MonkeyOCRv2 pipeline) is deliberately not implemented, per this phase's plan (option a: skip). No MonkeyOCRv2 vLLM endpoint has been available — `examples/monkeyocrv2_smoke.rs` exists, unrun, same as dots.ocr's.

`T-4.1`–`T-4.3` are implemented (`adapters/native.rs`, `#[cfg(feature = "native")]`): a **zero-model** protocol embedding `opensource/liteparse` (a first-party Rust library, not a wire protocol — no reverse-engineering needed) via `LiteParse::new(LiteParseConfig { ocr_enabled: false, .. }).parse_input(PdfInput::Bytes(..))`. Unlike P1–P3, this adapter's core method, `parse_document()`, is **tested against a real fixture PDF and genuinely works** (`ocr: 0.0ms` in liteparse's own timing log confirms OCR is correctly disabled; `extract: 36.3ms` shows real text-layer extraction) — no mocking needed since there's no network dependency, only the already-solved pdfium binary availability. One deliberate, documented trait-shape mismatch: `ProtocolAdapter::parse_page()` (the per-rasterized-page, per-request contract every other adapter implements) doesn't fit a library that parses a **whole document** in one call with its own internal PDFium/memory management — `NativeAdapter::parse_page()` is implemented but returns an explanatory `PageError`; the real entry point is the inherent (non-trait) `parse_document(source_path, pdf_bytes)`. Reconciling this with `scheduler.rs`'s per-page pipeline is deferred, likely a P8/router-time concern. `RawOutputFormat` gained a `None` variant (first change to that enum since P0) for this zero-wire-format case. `native` pulls in `pdfium` transitively and is opt-in, not default-on, same posture as `pdfium` itself.

`T-7.1`–`T-7.4` are implemented in `ingest.rs` (unconditionally, no feature gate — `detect_format`/`structured_bypass`/`normalize_format`/`ingest_document`, wired in the canonical `detect → structured_bypass? → normalize → (rasterize, separate)` order fixed by `ARCHITECTURE.md` §13.1a). `detect_format` uses the `file-format` crate (the same one `opensource/liteparse` already depends on for this) plus a filename-extension fallback for CSV (which has no reliable magic-byte signature). `structured_bypass` reads XLSX (`calamine`) / CSV (the `csv` crate — calamine 0.26 turned out **not** to support CSV despite the P7 plan's assumption it did via one shared `Reader` trait; a real, caught-and-corrected mistake, not a documented deviation) directly into `Block`s with `source = BlockSource::StructuredNative` (declared in P0's IR, unused until now) — **genuinely no model call, no rasterization**, fully tested with real CSV bytes (XLSX's zip-based binary format isn't hand-constructed in a unit test, a known gap). `normalize_format` shells out to `soffice`/`magick` with a bounded `tokio::time::timeout`, distinguishing `ToolNotFound` (hard env problem) / `ConversionTimedOut` (maybe retry-worthy) / `ConversionFailed` (tool ran, rejected input) — **fully tested for the failure paths** (missing-binary and timeout, via an overridable `ToolNames` struct so tests don't depend on `soffice`/`magick` actually being absent) since neither LibreOffice nor ImageMagick is installed in this environment; the real conversion *success* path (T-7.3's actual DOCX/PPTX/image→PDF output) remains unverified until those tools are available, and T-7.5 (perf/failure-rate evaluation) is documented as a design-and-degradation-strategy note on `normalize_format()` rather than measured real timing, for the same reason. `otsl::escape_html` was made `pub(crate)` and reused directly from `ingest.rs` — the first real cross-module code reuse beyond the adapter-level otsl/formula_repair sharing from P1–P3.

`T-8.1`–`T-8.3` are implemented, and **this phase's core claim is genuinely verified end-to-end**: `uparser classify <fixture.pdf>` (with `--features native`) prints a real `DocumentProfile` with `dominant_content: "text_dominant"`, `kind: "report"`, `kind_confidence: 0.8` for a real digitally-native PDF — the exact "digitally-native long text → native" split T-8.1's acceptance criterion asks for, validated against real liteparse output, not a mock. `types.rs`'s P0-era `DocumentProfile` stub (`{ notes: Vec<String> }`) was replaced outright with the full `ARCHITECTURE.md` §13.3 shape (`DocumentKind`/`ContentMix`/`ProfileLevel`/`PageProfile`/`DocumentProfile`, plus `TableSubtype`/`ChartSubtype` declared for shape-compatibility though genuinely unused — they're L3-only). `profiler.rs`'s L2 layer calls `liteparse::LiteParse::is_complex()` directly (not reimplemented) per the architecture doc's explicit instruction, mapping its `PageComplexityStats`/`LayoutComplexityStats` into our `PageProfile` — `has_chart_region` is an honest proxy (`figure_coverage >= 0.2 && !has_table_region`, reusing liteparse's own `DENSE_GRAPHICS_MIN_COVERAGE` constant), not a confident chart classifier, since real chart detection is L3-only. `router.rs::route()` implements the §13.4 table in order with an unconditional fallback row (never panics); its `"pipeline"` protocol recommendation is a string label only — no `pipeline` adapter exists yet (P5's job). **P6 (PaddleOCR + reading-order fallback, T-6.1–T-6.4 all implemented)**: adds `reading_order.rs` (new, shared) and `adapters/paddleocr.rs`. `reading_order.rs::assign_reading_order()` is a from-scratch recursive XY-cut (projection-profile splitting: find a clean horizontal or vertical gap partitioning the block set into non-overlapping bands, recurse into each; a genuinely tangled/overlapping set falls back to sorting by `(y0, x0)`) — deliberately **not** a port of `opensource/liteparse`'s `projection.rs` (~5500 lines operating on liteparse's own per-character text items, a different problem shape from ordering already-detected `Block` bboxes) and has no `native`-feature dependency, since both its consumers (`paddleocr`, `pipeline`) are unconditional core adapters, not feature-gated. **A real design decision surfaced by its own test suite**: the two candidate split axes must be tried **column-first, then row** (not the other, more "natural-sounding" order) — a two-column layout's stacked left/right blocks are geometrically ambiguous between "read column-by-column" and "read row-by-row" from bboxes alone, and only column-first priority produces the correct left-column-then-right-column order a real multi-column document needs; this was caught by `two_column_layout_reads_left_column_then_right_column` actually failing on the first (row-first) implementation, not assumed correct upfront. T-6.1 (PaddleOCR/PaddleX service-contract confirmation, `ARCHITECTURE.md` §8) has the same "no real deployment to reverse-engineer against" gap as P5's Pipeline Model Serving — PaddleX/PaddleServing/PaddleOCR's own HTTP demo are all real options with no single canonical schema, so `adapters/paddleocr.rs` documents and implements its own minimal, reasonable REST contract (`PaddleOcrRequest`/`PaddleOcrResponse`, reusing `pipeline_serving::StageImage`'s base64-PNG shape) rather than guessing at an unconfirmed real one, offline-tested via `MockDispatch` same as every prior adapter. T-6.3 (`Geometry::Polygon` handling) turned out to need **no new postprocess/render code at all**: `postprocess.rs::merge_paragraphs_by_geometry` already only reads `bbox_px` (never `geom` directly), and `geometry::geometry_bounds()` (declared back in an earlier phase, previously unused) already computes a polygon's bounding rect — so `paddleocr.rs` just calls it when building blocks, and a new test (`merges_polygon_shaped_paddleocr_blocks_via_their_bounding_rect`) proves polygon-sourced blocks merge identically to rect-sourced ones without any special-casing; `render::to_json`'s existing serde derive already round-trips `Geometry::Polygon` losslessly (no change needed there either). `category_vocab()` returns a single-element `&["text"]` (T-6.4's "无分类映射为 text" — there is no native layout vocabulary to map from at all, unlike every other adapter's `category_map.rs` function). **`pipeline.rs` was also retrofitted** to call `reading_order::assign_reading_order` directly (previously left `reading_order: None` per the P5-era plan, deferred exactly to "P6") — both `paddleocr` and `pipeline` declare `provides_reading_order() = false` (honestly describing that neither protocol's own model output carries an order signal) but call the fallback function directly inside `parse_page` rather than waiting on `scheduler.rs` to generically wire it (a deferred gap, same category as `postprocess.rs` never having been scheduler-wired since P1). A pre-existing `BlockSource` mismatch was also caught and fixed in passing: `pipeline.rs`'s blocks were tagged `BlockSource::OcrPipeline` (P5), but that variant's documented intent is a no-layout detect+recognize flow (PaddleOCR's actual shape) — `pipeline` (which does have a distinct layout stage) now correctly uses `BlockSource::LayoutThenRecognize`, the same variant mineru-vlm uses for its structurally-identical two-stage shape. All new tests pass for real: 186 unit + 12 CLI tests (default features), 193 unit + 11 CLI tests (`--features native`) — no environment gaps this phase, unlike P5.

**P9 (cache + streaming + doctor + protocols + contract tests, T-9.1–T-9.6 all implemented, sub-key layering deferred)**: adds `cache.rs` (T-9.1) — content-hash keyed (`sha256(source bytes) + protocol + endpoint + model` via `ParamFingerprint`/`cache_key()`), storing full `ParseResult`s as one JSON file per entry under `<base_dir>/<hash[..2]>/<hash>.json` with a TTL (default 24h) and `get`/`put`/`stat`/`clear`. As predicted back in the P5-era plan text, this module needed **no external dependency and landed with full fidelity** — genuinely real, not offline-scoped like P5's `ort`/P1's endpoint gaps. §15's "profiler intermediate artifact sub-key" half is explicitly **not** built: nothing in this codebase currently produces a rasterized-page/thumbnail artifact as an independently cacheable value (`profiler.rs`'s `profile_l2` computes straight from raw bytes in one `liteparse::is_complex()` call), so that layer is deferred until a real intermediate exists to key on rather than speculatively caching a shape nothing consumes. `cli.rs` gained `--no-cache`, `--stream`, and three new subcommands: `cache stat|clear`, `doctor <protocol> [--endpoint]`, `protocols`. `scheduler.rs` gained `run_streaming()` (T-9.2) — same windowed/concurrency-bounded execution as `run()`, but invokes a per-window callback as soon as that window completes (verified via a test asserting window sizes `[4, 4, 2]` for 10 pages at window_size=4) so `--stream` can emit NDJSON incrementally instead of building one aggregate `ParseResult`; only a transport-level failure counts as unreachable) for HTTP-backed protocols, and for `pipeline` reports real local `std::thread::available_parallelism()` CPU count + `/proc/meminfo`'s `MemAvailable` (no new `sysinfo`-style dependency) as a non-binding Local/Remote advisory. `protocols` (T-9.4) required one small `Registry::names()` addition and otherwise just introspects every built-in adapter's existing trait methods into JSON. **A real test-isolation bug was caught and fixed while wiring this up**: `cache::default_cache_dir()` unconditionally resolved to the real `$HOME/.cache/uparser`, so running the CLI test suite was silently writing/reading real cache entries on the development machine — several tests share the literal bytes `b"fake pdf bytes"` + protocol `mock`, which would hash to the *same* cache key and risk cross-test collisions under parallel test execution.
